# apps/api load tests

Manual, on-demand k6 scripts for the three "hottest path" categories in
`apps/api`. **These do not run in CI** — they are a local/staging operator
tool, not part of `pnpm test`. See "CI safety" at the bottom.

Results from the last recorded run are written up in
[`docs/load-test-results.md`](../../../docs/load-test-results.md).

## What's here

```
loadtest/
  stubs/chain-stub.ts        local stand-in for Solana RPC, Robinhood (EVM) RPC,
                              and the Coinbase-shaped price oracle
  seed.ts                    seeds Postgres with launch-day-scale board data
  mint-tokens.ts             mints JWTs for the wallets seed.ts generated
  lib/wallets.ts             synthetic Solana/EVM address generation
  k6/
    lib/config.js            shared fixture loading + synthetic-IP helpers
    board-read.js             GET /tokens, /tokens/:sym, /candles, /trades + WS
    quote-burst.js            GET /tokens/:sym/quote under a simulated "pump"
    trade-launch-prepare.js   POST /trade/prepare + POST /launch/prepare
  fixtures/                  generated by seed.ts/mint-tokens.ts — gitignored
  results/                   k6 --summary-export output — gitignored
```

## Why a chain stub?

`apps/api/src/server.ts` always constructs real `SolanaRpc` / `EvmRpc` /
`HttpPriceOracle` clients — there's no env toggle to swap in the in-memory
fakes the unit tests use. Load-testing `/trade/prepare` (calls
`getLatestBlockhash` + `getBalance` on every request) or a cold `/quote`
against the _real_ public Solana RPC or a public Robinhood RPC would measure
those providers' rate limits, not this API, and risks this machine's IP
getting throttled or banned mid-run. `stubs/chain-stub.ts` answers exactly the
handful of JSON-RPC methods and HTTP routes those two RPC clients and the
oracle client actually call, with a configurable artificial latency (default
60ms, a realistic paid-provider RTT).

## Running the full stack locally

1. **Postgres + Redis** (adjust ports if 5432/6379 are taken locally):

   ```bash
   POSTGRES_PORT=55433 REDIS_PORT=63799 docker compose up -d
   ```

2. **Migrate**:

   ```bash
   cd apps/api
   DATABASE_URL=postgres://stonkz:stonkz@localhost:55433/stonkz pnpm migrate
   ```

3. **Chain stub** (in its own terminal):

   ```bash
   pnpm loadtest:stub
   # -> SOLANA_RPC_URL=http://127.0.0.1:9081/solana
   #    RH_RPC_URL=http://127.0.0.1:9081/evm
   #    PRICE_ORACLE_URL=http://127.0.0.1:9081
   ```

4. **Seed the board** (hundreds of tokens/net with real curve state, trade
   history, candles, holder snapshots):

   ```bash
   DATABASE_URL=postgres://stonkz:stonkz@localhost:55433/stonkz \
     pnpm loadtest:seed -- --tokens-per-net=400 --wallets-per-net=150
   ```

5. **Mint JWTs** for the seeded wallets (must match the API's `JWT_SECRET`/
   `JWT_ISSUER`/`ACCESS_TOKEN_TTL_SECONDS` — omit the env vars to use this
   repo's dev defaults, fine for a local stack only):

   ```bash
   pnpm loadtest:mint
   ```

6. **Start the API** against the stub and the seeded DB:

   ```bash
   DATABASE_URL=postgres://stonkz:stonkz@localhost:55433/stonkz \
   REDIS_URL=redis://localhost:63799 \
   SOLANA_RPC_URL=http://127.0.0.1:9081/solana \
   RH_RPC_URL=http://127.0.0.1:9081/evm \
   PRICE_ORACLE_URL=http://127.0.0.1:9081 \
     pnpm dev
   ```

7. (Optional, for the WS board/token scenario to carry real traffic) start
   `apps/indexer` on its fixture source alongside — see the indexer runbook
   ([`docs/indexer-runbooks.md`](../../../docs/indexer-runbooks.md)) and
   `apps/indexer/README.md` for how to run it against the same DB/Redis.
   Without it, the WS scenario still exercises connect/subscribe/hold at full
   scale, it just won't see new board/trade broadcasts after indexer catch-up.

8. **Install k6** if you don't have it (`brew install k6`, or see
   <https://k6.io/docs/get-started/installation/>).

## Running the scripts

Each script reads `loadtest/fixtures/manifest.json` (and `auth.json` for the
write-path script) via k6's `open()`, resolved relative to
`k6/lib/config.js` — always run k6 from `apps/api/loadtest/k6/`.

```bash
cd apps/api/loadtest/k6

# Board/token reads + WS subscribers
k6 run board-read.js
BOARD_VUS=150 WS_VUS=150 DURATION=3m k6 run board-read.js

# Quote burst ("pump")
k6 run quote-burst.js
STEADY_RATE=15 PUMP_RATE=120 k6 run quote-burst.js

# Trade + launch prepare (writes, authenticated)
k6 run trade-launch-prepare.js
TRADE_RATE=20 LAUNCH_RATE=2 DURATION=90s k6 run trade-launch-prepare.js
```

Useful env vars for all scripts: `BASE_URL` (default
`http://127.0.0.1:8787`), `WS_URL` (default `ws://127.0.0.1:8787/ws`),
`LOADTEST_NET` (`SOL` or `RH`, default `SOL`).

Save a machine-readable summary alongside a run with:

```bash
k6 run --summary-export=../results/board-read-summary.json board-read.js
```

## CI safety

- `pnpm test` (see `apps/api/package.json` and the root CI workflow) never
  invokes anything under `loadtest/` — there is no `test` script here that
  globs this directory, and `loadtest:*` are separate, manually-invoked
  scripts.
- `loadtest/fixtures/*.json` (freshly generated wallets/keys/manifests) and
  `loadtest/results/` (this machine's k6 summaries) are gitignored — nothing
  generated by a run gets committed by accident.
- k6 itself is not a project dependency (no `package.json` entry) — it's an
  external CLI tool, matching how this repo already treats Docker Compose for
  local Postgres/Redis.
